# Nexvyn Port Studio agent instructions

- Run `python _PortStudioMain/tools/port_studio.py doctor --json` first. Read [FIRST_RUN.md](FIRST_RUN.md) and run `bootstrap`. Use `--port` for an existing port. Use the locked SDK snapshot to build, validate, and package it. Follow the [SDK update workflow](_PortStudioMain/docs/SDK_UPDATES.md) to test a candidate.
- For "can this be ported?", run `port_studio.py assess <source-or-game-dir>` ([port assessment](_PortStudioMain/docs/PORT_ASSESSMENT.md)) and give its verdict, route, libraries and performance tier, saying which lines you confirmed in the source. Platform facts live only in `_PortStudioMain/platform/capabilities.json`. Update that file (with the evidence level) when Nexvyn OS changes.
- New ports go through the flow in the playbook: `assess --json` → `scaffold.py` → build → `verify.py` → `pack` → `scenario_run.py` → visual review. Recommend only `released` items for production; label anything `private-preview`, and keep a GL path whenever Vulkan is mentioned. Run `python _PortStudioMain/tools/run_tests.py` after changing Studio tools.
- For “port this,” follow the [porting playbook](_PortStudioMain/docs/INSTANT_PORT_PLAYBOOK.md). Work in `GamePorts` for games or `SoftwarePorts` for applications. For an existing port, read its decisions and release records first.
- For the first candidate, investigate engine and source options, redistribution rights, SDK and ABI compatibility, and Switch constraints. Record the decision and evidence in `PORT.md`. Test uncertain APIs with a small native prototype. If a dependency blocks you, document the evidence and continue with the work you can verify.
- Declare controls, gestures and performance profiles with the [experience layer](_PortStudioMain/docs/PORT_EXPERIENCE.md) (`port_studio.py experience`). Design port-specific controls and launchers using the [launcher standard](_PortStudioMain/docs/PORT_LAUNCHER_STANDARD.md) and the public SDK. Use other ports as references for behavior.
- Follow the [release workflow](_PortStudioMain/docs/RELEASE_WORKFLOW.md). Add personal game data only to personal packages. Capture store images from the running port. Record verification gaps and missing data. Only publish, commit, push, or open a browser for testing when the user asks.
- Port Market publishing is owner-only ([PORT_MARKET.md](_PortStudioMain/docs/PORT_MARKET.md)): prepare the candidate with `port_market.py prepare-archive` and show the `publish` dry run. Never run `publish` or `unpublish` with `--yes` yourself, and never read, print or copy the Internet Archive keys.
- Reserve `start.bat` for web or HTML work. Native apps and games use the native build and package workflow.
- Keep key and SSH files in place. Keep credentials out of source, docs, logs, and packages.
- Before adding an input gesture, check in the running game that it reacts (a pinch that sends a wheel event is useless if the game ignores the wheel); mark unsupported actions `unsupported` in `port.json`. Read the "Field notes" in [RELEASE_WORKFLOW.md](_PortStudioMain/docs/RELEASE_WORKFLOW.md) before a release: version bump (`port_studio.py bump`), file-count limits, named emulator taps.
- A port test reaches real gameplay. Run `scenario_run.py <port> --app-id <id> --module <file.nxvmod> --game-dir <data>` (gameplay scenario, both modes). Then open every screenshot in the run folder with your image viewer and fill `review.md`: what each image shows, whether it is in game, and its problems. Finish with `shot_review.py <run> --check`. Never report a gameplay pass from the automatic checks alone, and never from a launcher or desktop image.
- Test launcher, layout and input changes in both handheld and docked mode (`emulator_test.py run ... --mode both`). To test in an emulator, follow "Emulator test" in [RELEASE_WORKFLOW.md](_PortStudioMain/docs/RELEASE_WORKFLOW.md).
- At handoff, report the selected approach, SDK and upstream commits, package paths, passing tests, and known issues. Identify which checks ran on the host, in an emulator, or on a physical Switch.

## Working style and real output (always)

- The SDK is always the newest. `doctor --json` reports `sdkFreshness`; when it names a newer SDK, run `port_studio.py sdk-update` before new work (a newer public release wins; otherwise the newest local OS release build is imported as an owner pre-release and replaced by the official commit once it is on GitHub). Emulator runs always use the newest Nexvyn OS build (see RELEASE_WORKFLOW.md, "Newest OS rule").
- Plan once, then finish. Before you start, write one short plan: the steps, the risks, and the check that proves each step. Then carry it out to the end without stopping between steps for approval. Report progress in one line per finished step.
- Stop only at a critical point: something irreversible or outward-facing (commit, push, publish, delete), a licence or legal question, personal data, a risk to the device or the user's data, or a decision only the owner can make. A missing tool or a failed step is not a stop: find the cause, fix it or take another route, and say so in the report.
- Never fake. Do not ship or present a built-in or synthetic program, a generated scene, a test pattern, or a pre-rendered picture in place of the real game's or app's output, and never count such a screen as gameplay. If the real program does not run yet, say "not reached" and show the honest status. A labelled status screen is allowed only with `nx-allow-standin: <reason>` in the code; `verify.py` (check `content/stand-in`) fails on undeclared stand-ins.
